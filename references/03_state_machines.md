# 03 状態遷移の雛形（契約・決済試行・停止・ジョブ）

この資料で決まること
- 契約と決済試行に、どんな状態を持たせるか（語彙）
- どの出来事でどの状態に動くか（遷移表）。書き込む処理がない「読むだけの状態」を作らないための確認
- 日数（猶予・停止・削除）を1か所にまとめる表の型と、ジョブを1回しか動かさない仕組み

状態遷移は、実装したあとにコードから起こし直す価値がある。設計時の図と実装がずれていることが多く、ずれの一覧がそのままレビューの材料になる（末尾「読み取りで見つかりやすい食い違い」）。

---

## 1. 状態の語彙

| 対象 | 値 | 設計上の注意 |
|---|---|---|
| 契約（subscription） | `pending_payment` / `active` / `past_due` / `restricted` / `suspended` / `ended` | 定義した状態ごとに「どこで書き込むか」を確認する。enum にあるのに誰も書かない状態ができやすい（例: suspended を enum に置いたが、停止は別テーブルの `suspended_at` で表していた） |
| 申込（application） | `pending` / `active` / `past_due` / `cancelled` | 「支払われたか」だけを追う証憑。契約が終わっても申込の状態は自動では変えない。変えるなら、その処理を明示的に持つ |
| 決済の試行（billing_attempt） | `pending` / `charging` / `succeeded` / `failed` / `unknown` | `failed` からは遷移しない。再試行は `retry_of_attempt_id` を持つ新しい行にする。`unknown` は「PSP に聞くまで分からない」状態で、照合ジョブだけが動かす |
| 試行の種類 | `initial_charge` / `cycle_charge` / `slot_charge` / `cancellation_forfeit` | 金額の出所（初回／更新／追加枠／解約時の未収放棄）で分ける。集計で必要になる |
| 請求先の種類 | `card` / `invoice` | 同じ契約モデルに type で持つ（02 の論点5） |
| 委任（第三者支払い） | `pending` / `completed` / `revoked` / `expired` / `declined` | 期限切れはジョブではなく、開いたときに判定してよい |
| アプリ停止の理由 | `payment_overdue` / `free_limit_exceeded` / `dormant` / `manual` | 理由ごとに再開の条件が違う。理由を持たないと「払ったのに戻らない」「別の理由で止めたものまで戻る」が起きる |
| ジョブの実行 | `running` / `succeeded` / `failed` | `(job_name, run_date)` を一意にし、1日1回しか動かないようにする |

## 2. 契約の遷移

| From | To | きっかけ | 書くときの注意 |
|---|---|---|---|
| （新規） | `pending_payment` | カードで有料化を開始／委任リンクの受諾 | 決済が通るまでは権利を開放しない |
| `pending_payment` | `active` | 初回課金の成功／請求書契約の有効化／成否不明の照合で「支払い済み」と判明 | 照合経由でも同じ処理を通す |
| `active` | `past_due` | 月次課金の失敗／照合で失敗が確定／更新日に支払者が辞退済み | **`past_due_since` は既にあれば上書きしない**（起算点を動かさない） |
| `past_due` | `restricted` | 滞納が猶予日数に達した（毎日の未収処理で判定） | 新規作成・招待・独自ドメインなど「増やす操作」を全部止める。1経路だけ止めると抜け道になる |
| `past_due` / `restricted` | `active` | 支払いが通った（再試行・手動支払い・カード変更後の回収） | `past_due_since` を null に戻す。復帰の起算日は本来の更新日（据え置き） |
| `past_due` / `restricted` | `ended` | 滞納が削除日数に達し、削除がすべて終わった | **1件でも削除に失敗していれば終了させない**。人に確認を依頼する。先に終了させると、失敗した削除が宙に浮く |
| `active` / `past_due` / `restricted` | `ended` | 解約予約の期日が来た | 期末23:59:59.999 と課金ジョブのどちらが先かを規則で固定する |
| 終了以外すべて | `ended` | ワークスペース（課金単位）の削除 | 解約予約済み＋返金なしへの同意を前提にする。未収がある場合は放棄記録を作るかどうかを決めておく（02 の論点21） |

「終了後に遅れて届いた決済成功」は、記録だけ残して契約は復活させない。

## 3. 決済試行の遷移

| From | To | きっかけ |
|---|---|---|
| `pending` | `charging` | PSP に送る直前。金額が 0 なら PSP を呼ばず直接 `succeeded`（免除理由つき） |
| `charging` | `succeeded` | PSP が成功を返した **かつ** DB に反映できた |
| `charging` | `failed` | 4xx の確定拒否（429 を除く） |
| `charging` | `unknown` | 429／5xx／通信断／3DS 待ち／**PSP は成功したが DB 反映に失敗**／後処理（メール・通知）の失敗 |
| `unknown` | `succeeded` / `failed` | 復旧（照合）ジョブが PSP に問い合わせた結果。PSP 側に見つからないまま1日を過ぎたものは `charge_not_found` として `failed` にする |

`unknown` の行には、PSP 側の charge ID を必ず残す。ID が無いと照合できない（04 の「決済成功後の DB 失敗」）。

## 4. 日数一覧の雛形

日数はすべて定数にまとめ、起算点も一緒に書く。規約には書かず、ガイド・FAQ・手順書に置く（06 参照）。

| 定数 | 起算点 | 意味 |
|---|---|---|
| 自動再試行 | 前回の自動失敗 | N1・N2・N3 日後に再試行し、4回目はしない。手動操作で日程は狂わない |
| 停止までの猶予（SUSPEND_DAYS） | `past_due_since` | 制限し、公開を止める |
| 削除の最終通知（DELETE_DAYS − 14） | 同上 | データの書き出しを促す |
| 削除（DELETE_DAYS） | 同上 | 削除が終わってから契約を `ended` にする |
| 経過日数の数え方 | `floor((now − since) / 1日)` | 「当日0時台に止まる」バグの温床。期限日は23:59まで使え、停止は翌日0時台、と決めて `remainingDays >= 0` の境界をテストする |
| 停止中アプリの枠免除 | 停止日時 | 停止中のものを本数に数えない期間 |
| 無料プランの放置停止の予告 | 最終活動 | 別制度なら別の起算点を持つ |
| 無料プランの停止可能日 | `max(最終活動＋N, 予告の受付＋7日)` | 予告から最低7日は空ける |
| 委任リンクの期限 | 発行日 | 期限の選択肢を用意する |

## 5. ジョブを1回しか動かさない

- ジョブ実行テーブルに `(job_name, run_date)` の一意制約。同じ日に2回起動しても2回目は何もしない。
- 停止・削除・通知のような「契約ごとに1回」の処理は、`<種類>:<契約ID>:<滞納開始日>` のような一意キーで記録する。滞納開始日を含めると、復帰してまた滞納したときに再度動ける。
- 実行中の排他はトランザクション単位の advisory lock（セッションロックではない）。
- 過去日付での再実行（`--at 2026-01-01` のような引数）は便利だが、実行記録を残さないと事故の温床になる。
- 通知の失敗は「成功」にしない。失敗を記録して再送する（outbox）。通知失敗で契約状態を変えない。

---

## 6. 2つの削除経路を混ぜない

「支払いの滞納で削除する」経路と、「無料プランの放置で削除する」経路は起動元（`triggeredBy`）で分け、保留の印（`manual_hold`）も別に持つ。混ぜると、一方の経路でもう一方の対象が消える。特に、滞納で止めたアプリが「放置」と見なされて別の経路で消える事故が起きやすい（07 のタイムライン E+31 の確認項目）。

---

## 7. 実装をコードから読み直すと見つかりやすい食い違い

状態遷移図を、設計書からではなく実際のコードから起こし直すと、次のような食い違いがよく出る。図に行番号を添えておくと、レビューがそのまま修正指示になる。

1. 第三者支払いの受諾で、PSP への課金をトランザクションの中で呼んでいる。課金は成立したのに DB で失敗すると、試行の記録ごと巻き戻り、PSP 側の顧客だけが残る。
2. 月次の失敗で `resolved_at` が入らず、いつまでも未解決に見える。
3. 領収書の宛名の出どころが支払い経路（本人カード／委任／請求書）ごとに違う。
4. 照合が1日1回なので、「引き落とされたのに有効にならない」時間が最大で丸1日ある。顧客向け画面に「確認中」の表示が要る。
5. 停止判定の式（滞納日数の計算）が、顧客向けバナー・運営画面・復旧ジョブの3か所にあり、少しずつ違う。
6. 未納歴の判定が「`status='ended' AND past_due_since IS NOT NULL`」のように残った列に依存している。掃除ジョブが列を消すと履歴が全部消える。スキーマにコメントで残す。
7. 削除が1件でも失敗すると契約が終了せず滞納のまま残る。運営画面に「削除待ちで止まっている契約」の一覧が要る。
8. ワークスペース削除が `cancel_at_period_end` を戻してしまい、未納歴に数えられる（または数えられない）。
