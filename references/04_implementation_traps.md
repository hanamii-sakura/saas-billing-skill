# 04 実装の罠（9分類）と、外部との境界の監査

この資料で決まること
- コードレビューとテストで狙い撃ちにする、課金でよく起きる不具合の型
- 「安全側に倒したつもり」の設計が事実を捨てる場面
- PSP（Pay.jp／Stripe）の公式ドキュメントと自分の思い込みを突き合わせる監査のやり方と、フラグを ON にする前の必須修正の型

いずれも、単体テストが全部通った状態で見つかったものが多い。テストが同じ思い込みを共有していたからで、実物（本物の DB・本物の PSP のテストモード）で一度動かすことが唯一の対策だった場面が何度もあった。

## 1. DB 制約と同時実行

- **NULL の列は部分一意インデックスをすり抜ける。** `UNIQUE (workspace_id) WHERE status <> 'ended'` は、`workspace_id = NULL` の行を何本でも通す（PostgreSQL は NULL 同士を別値とみなす）。二重課金の最後の砦のつもりだった制約が効いていなかった。対策は `CHECK (status = 'ended' OR workspace_id IS NOT NULL)` か、COALESCE を使った式インデックス。NULL の重複挿入が拒否されるテストを1本置く。
- **リクエストごとの冪等キーは、別々のリクエストの二重実行を止めない。** 「枠を1本足す」を別の操作IDで2本同時に送ると、両方が古い本数を読み、両方が課金し、結果は +1 のまま。対策は行ロックして読み直してから課金する。
- **確認してから作る（check-then-create）競合。** `assertCanCreate()` の後に別トランザクションで `create()` すると、並列リクエストが両方通る。無料枠の上限判定で、5本同時に作成すると5本できた。対策は1つのトランザクション内で親行を `SELECT ... FOR UPDATE`（または advisory lock）→ 数え直し → insert。作成の経路（画面・API・外部連携）は全部同じ関数を通す。ルート側の事前チェックは体験のためだけ。
- **失敗した課金の再試行が、何度でも回収する。** 「カード変更時に失敗分を再試行」が、カード変更のたび・並列呼び出しのたびに同じ失敗分を課金した。対策は元の試行に「回収済み」を付け、1つの失敗につき回収は1回に限定する。
- **論理削除した行を数える。** `deletedAt IS NULL` を付け忘れた `_count` が、新規作成を誤って拒否し、自動減枠も壊す。

## 2. 金額計算とプランデータ

- **負の割引が請求額を増やす。** `min(割引, 価格)` には下限も要る。`0..価格` に丸めるか、負なら拒否する。
- **seed の upsert が凍結済みの価格を書き換える。** `(code, version)` をキーにした `upsert({update: plan})` は、既存契約が指しているバージョンの価格を黙って変える。プランのバージョンは不変として insert のみにし、seed と DB が食い違ったら失敗させる。
- **見積の比較に生成項目を含める。** 見積を再計算すると `expiresAt` が変わるので、クライアントが持ってきた見積と完全一致で比べると、実際の確定操作がほぼ毎回 409 になる。テストは固定の `NOW` を使っていたので気づかなかった。比べるのは金額に効く項目だけ。
- **領収書の行が二重に数える。** 「基本料＝定価−割引」の行と別に「追加枠」の行を作ると、実際の2倍の額が印字される。0円の免除も正の行として出た。領収書の行は、課金に使ったのと同じ凍結済みの内訳から作る。

## 3. 日付と課金サイクル

- **N回目の課金日は、いつも最初のアンカーから計算する。** 前回の日付から1か月足していくと、31日を30日に丸めた時点で二度と31日に戻らない。`anchor + N か月` を月末で丸める。
- **「更新日」が2つの意味で使われる。** 仕様は期間の終わり（5/14）で、FAQ は課金日（5/15）だった。解約期限の説明が資料ごとに1日ずれる。「期間末」と「課金日」を別の言葉として持つ。
- **JST の期限を UTC で保存する。** 「X日 23:59:59.999 JST」は「X日 14:59:59.999 UTC」。正しく実装していても、テストデータを作るときに前日になる。pg の raw クライアントに `Date` を渡すと timestamp（time zone なし）列にローカル時刻で入って9時間ずれる。ISO 文字列で渡すか、型パーサを固定する。
- **0時のスナップショットで数えると、その日に作って消したものが課金されない。** 「その日のどこかの時点で存在した」で数える。
- **サイクルを途中で終える規則。** アップグレードで日割りするなら、分母がサイクルの全日数か使った日数か（4倍以上違った例がある）、境界日がどちらのサイクルに属するかを決める。
- **契約が終わった後の失敗課金に行き場がない。** 再試行・督促・放棄はどれも「生きている契約」を前提にしていた。失敗経路はすべて明示的な終点（放棄記録など）に着地させる。
- **更新日当日の購入。** 更新日に買った追加枠が、自動減枠ジョブに没収された。購入がどのサイクルに属するかを記録する。
- **期限日の当日0時台に止まる。** `remainingDays > 0` を `>= 0` にするだけの差。画面と見積は翌日停止と表示しているのに、ジョブは当日に止めた。境界のテストを1本置く。

## 4. PSP は成功したのに DB が失敗した

- PSP が課金成功を返した直後に DB トランザクションが失敗すると、試行が `charging` のまま残り、`unknown` にならず、日次の照合にも拾われない。
- 悪い場合、charge ID そのものが失われる。ヘルパーの中で例外が起きると、呼び出し元は ID を受け取れない。対策:
  - `onChargeCreated` のようなコールバックで、ID を受け取った瞬間に保存する
  - catch ブロックで必ず ID を保存し、試行を `unknown` にする
  - PSP の metadata に試行 ID を入れ、照合ジョブが逆引きできるようにする
- 冪等キーが無い PSP（Pay.jp）では、タイムアウトを「結果不明」として照合に回す。単純な再送は二重課金になる。Stripe なら `Idempotency-Key` を付けて再送できる（それでも照合は要る）。

## 5. Webhook

- **すべてのイベント種別で再取得する。** ある分岐（dispute.created）だけ API での再取得より前に return していて、再送・livemode・metadata・試行の検証を全部飛ばしていた。順番は「受信記録 → API で再取得 → 検証 → 処理」。
- **常に 200 を返すと PSP の再送が止まる。** DB 障害時は 5xx を返す。Pay.jp は 2xx 以外なら再送する（回数は公式ドキュメントで確認）。Stripe も 2xx 以外を再送する。
- **通知の失敗を「成功」で記録した。** チャージバックの Slack 通知に失敗しても完了扱いになり、誰にも知らされなかった。失敗として記録し、再通知する。
- **本文の形の思い込み。** `data.object` を読んでいたが、実際のイベントはリソースが `data` 直下だった。テストは古い形だけ。フィクスチャは本物のイベントから取る。
- **再送イベントは違う。** ダッシュボードからの再送では最上位の `livemode` が true なのに、再取得したイベントと charge は false だった。信じるのは再取得した方。ダッシュボードのダミーイベントは再取得に失敗する。
- **イベント ID で重複排除する。** 理由コードは公式のコード表に基づく明示リストにする。`code.includes('card')` のような曖昧な分類はやめる。

## 6. カードとフロントの境界

- **Checkout のスクリプトはシングルトン。** `window.PayjpCheckout ||= ...` のため、SPA でダイアログを開き直すとカード入力ボタンが二度と出ない。マウントしたままにするか、グローバルを掃除するか、payjp.js に移す。
- **トークンのコールバックは文字列ではなくオブジェクトを渡す。** 文字列と思い込んで `[object Object]` を送り、`invalid_id` になった（この1件が境界監査の発端だった）。
- **3DS（iframe 型）はトークン作成時に認証が済む。** 「finish が要る」というコメントとテストの根拠が誤りだった。メール・電話の追加属性は渡す（将来必須になると予告されている）。保存カードでの課金では 3DS を要求しない。顧客が操作する場面（カード変更・再契約）の 3DS は場面ごとに定義する。Stripe なら PaymentIntent の `off_session` と SCA の扱いを公式で確認する。
- **成否不明のカード操作をラッチする。** 書き込みの応答が失われた（500、status 0、`processing`）あと、古い読み取りがまだ `quoted` を示しているだけでカード入力を再表示しない。サーバーが後の状態を返すまで「カード確認中」を保つ。ただし**ラッチに期限を持たせる**。期限なしのラッチは、タブを閉じるまで復帰できない詰まりを作った（60秒程度の窓で外す）。
- **何でも「カード拒否」にしない。**
  - 429 はレート制限（Pay.jp のテストモードは秒2リクエスト程度）。再試行し、督促には回さない
  - `missing_card` や 3DS のエラーコードは顧客のカードの問題ではない
  - PSP のエラーコードを保存する。`failureMessage: null` で潰さない
  - クライアント側の失敗理由（通信断など）を「Visa／Mastercard をご利用ください」で上書きしない
- **カードの同一性は fingerprint で見る。** 下4桁＋有効期限では家族カードを誤同定する。重複カードのエラーコードは2種類ある。顧客のカード一覧は既定で10件ページングされるので、`default_card` は個別に取る。402 のエラー本文に付く charge ID を保存しないと、後の `charge.failed` Webhook が照合不能になる。
- **リクエスト本文を検証する。** 未検証の `req.json()` は null や欠損で 500 を返す。400 を返す。

## 7. 返金と突合

- **部分返金済みを照合対象から外していた。** 一部返金した支払いを除外していたため、追加の返金が同期されない。累計返金額で照合し、金額が戻らないよう条件付き更新にする。
- 返金の照合は返金可能期間（Pay.jp は売上から180日）に絞り、スロットリングする。件数が増えると 429 になる。

## 8. 運用と状態設計

- **履歴を「残った列」で表している。** 「未納歴」＝ `status='ended' AND past_due_since IS NOT NULL` のような定義は、掃除ジョブが列を消すと履歴ごと消える。スキーマのコメントに書く。
- **削除と終了の順番。** 停止 → 削除 → 終了 の順が前提になっている（再試行ジョブが `past_due`/`restricted` だけを拾う）。先に終了させると、未完了の削除が宙に浮く。
- **停止判定の式を全部同じにする。** 顧客向けバナー・運営画面・復旧ジョブで同じ式を使う。「予定日を過ぎた」と「実際に止まった」は別に表示し、運営が見たいのは「過ぎたのに止まっていない」。
- **制限中は増やす操作を全部止める。** プロジェクト作成だけ止めて、招待と独自ドメインが開いていた。
- **ログが失敗を隠す。** 秘密を漏らさないための許可リスト型ロガー（メッセージとスタックを捨てる）は目的には合っているが、束縛のない `catch {}` や「安全側」の既定値と組み合わさると、調査に必要な唯一の事実が消える。PSP のエラーコードと charge ID だけはログに残す。

## 9. 「安全側に倒したつもり」が事実を捨てる

同じ形で3回起きた。
- ログの許可リストが、エラーの中身を捨てる
- Webhook が常に 200 を返し、PSP の再送を止める
- `catch` して `unknown` に変えるだけで、原因を残さない

共通するのは「捨てた事実を誰にも知らせない」こと。安全側に倒すなら、倒したことを運営に通知する経路を同時に作る。

## 外部との境界の監査（3レーン）

きっかけは「トークンを文字列だと思い込んで `invalid_id`」の1件。型・コメント・テストの3層が同じ思い込みを共有していたので、外部の振る舞いを一次情報と突き合わせる監査を別枠でやった。

### 一次情報
- PSP 公式ドキュメントのローカル写し（API リファレンス・ガイド・ヘルプ記事）。取得日を残す
- Checkout／Elements のクライアントスクリプト本体（minify されていても読む）

### 3つのレーン（別々の担当で）
1. **サーバー API の契約**: 自分のコードが仮定している応答の形・エラーコード・ページング・上限を、リファレンスと1つずつ突き合わせる
2. **クライアント（Checkout）**: コールバックの引数の型、シングルトンか、開き直しの挙動、3DS の完了タイミング
3. **黙って捨てる仕組みとモック**: ロガーの許可リスト、常時 200、`catch {}`、そしてモックが本物の境界を消している箇所（Webhook の本文の形、顧客更新のエラー、エラー本文、Checkout ボタン丸ごと）

### 出力の型
- 確定した問題（コード引用・具体的な入力とタイミング・直し方）
- 疑わしい問題（裏取りが要る。公式で確認した結果も書く）
- モックで境界が消えていたテスト
- 同じ形で起きた理由
- **フラグ ON 前の必須修正**:
  - ON 前に必須: 顧客が詰まるもの／失敗理由の記録（課金と DB の両方）／Webhook のログ・通知と DB 障害時の 5xx／受信記録の形
  - 同じ PR で安く直せるもの: 429 を unknown に分類しスロットリング／誤った根拠のコメント／3DS の追加項目／状況別の失敗メッセージ
  - 再スモーク: 人が実際の Checkout 画面でカードを入れて通す。**迂回した場合はそう記録し、PASS にしない**
  - 確認して問題なかった項目も一覧に残す（認証方式、エンドポイント、3DS 保留の時間、保存カードでは 3DS を要求しないこと、イベント ID の重複排除、冪等キーの有無、metadata の上限、未承認ブランドはトークン作成時に弾かれること）

### Pay.jp と Stripe で違うところ（2026年9月時点。実装前に公式で再確認）

| 項目 | Pay.jp | Stripe |
|---|---|---|
| 冪等キー | なし。タイムアウトは成否不明として照合 | `Idempotency-Key` ヘッダあり。照合は別途要る |
| 保存カードでの課金 | customer に紐づくカードで charge。3DS は要求しない | PaymentIntent を `off_session: true` で確認。SCA の例外扱いを確認 |
| 3DS | Checkout の iframe 型はトークン作成時に認証。追加属性（メール・電話）を渡す | Payment Element／Checkout が自動で処理 |
| Webhook | 2xx 以外で再送（回数・間隔は公式で確認）。イベントは API で再取得できる | 署名検証必須。2xx 以外は最大3日程度再送 |
| テストモードのレート制限 | 低め（秒2程度）。E2E で 429 を踏む | 高め。それでも並列テストで踏むことはある |
| 返金可能期間 | 売上から180日 | カード会社と地域で異なる。公式で確認 |
| カード一覧 | 既定10件ページング | 既定10件ページング（`limit` で変更） |
