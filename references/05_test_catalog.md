# 05 テストケースの台帳と、本物の環境で再現する方法

この資料で決まること
- 課金のテストケースを「台帳」として持つときの項目と、テーマの網羅（15テーマ）
- 結果の4区分（pass／fail／not_executable／substitute）と、迂回して通したものを pass にしないためのルール
- 人が手でやったテストを、本物のサーバー・DB・PSP のテストモードで自動再現するハーネスの立て方

課金のテストは、モックで通したものが本物で落ちる、が普通に起きる（04 参照）。台帳は「何を確かめたか」より「何を確かめていないか」を残すためにある。

---

## 1. 台帳の項目（1ケースあたり）

`templates/cases.schema.json` に JSON Schema がある。

| 項目 | 中身 |
|---|---|
| `id` / `category` / `priority` | 例: BIL-001 ／ テーマ ／ P0・P1 |
| `title` / `goal` | 1行の題名と、何を確かめるか。**否定条件も書く**（例:「ダイアログを閉じただけでは作れないことも見る」） |
| `preconditions` | 前提の状態（プラン、カード有無、リソース本数、自分の権限） |
| `setup[]` | 前提の作り方（なければ新規作成、DB 起動など） |
| `testData[]` | テストカード番号、3DS の選択、金額や日数の境界値 |
| `steps[]` | 画面操作やコマンド |
| `expected[]` | 利用者に見える期待結果。「2件になっていたら NG」のように失敗の形も書く |
| `developerChecks[]` | DB の行数や状態、実行する結合テストのコマンド |
| `cleanup[]` | 後始末。別ケースで使い回すかどうか |
| `method` | `developer`（DB や CLI が要る）／`mixed`／`browser`（画面だけで完結） |
| `executability` / `needs[]` | いま実行できるか（`executable_now`／`needs_setup`／`not_executable`）と、足りないもの（シナリオ CLI、時刻の注入口、PSP の実鍵、公開 URL など）。台帳を作った時点で書く |
| `codeReview` | 既存コードに対して作るときだけ。`prediction`（いまのコードで pass／fail／unknown）、`reason`、`codeRef`（ファイルと行）。台帳がそのままコードレビューになる |
| `manual.status` / `manual.notes` | 人が手で実行した結果と備考（環境の不備も書く） |
| `auto.status` / `auto.reason` | 本物の環境で自動実行した結果（2章の4区分）。**実行していないうちは空欄**。予測（codeReview）と結果（auto）を混ぜない |

人が手でやった結果が「保留」「不合格」になった主な原因は、テストの内容より環境の不備だった。運営画面の許可リストが未設定、メール送信の TLS 失敗、拒否用テストカードが登録できない、前提状態を画面から作れない、の4つ。**前提状態を作るシナリオ CLI（ユーザー作成、カード登録、契約状態の直接投入、ジョブの論理日付実行）を先に用意する**と、人でも機械でも回る。

ただし、CLI がまだ無い段階で台帳を作るなら、手順を CLI に依存させない。SQL の INSERT や REPL からの関数呼び出しで、いま作れる前提の作り方を書く。CLI は `needs` に「作るもの」として挙げる。台帳の大半が存在しない道具を前提にしていると、誰も1件目を回せない。

テストデータは具体値で書く。「拒否されるカード」ではなく、PSP のテストカード番号（登録は通るが課金で落ちる番号と、登録で落ちる番号は別）、固定する日付（1月31日申込、閏年の2月）、境界値（期末 23:59:59.999 の前後1ミリ秒）。

## 2. 結果の4区分

```
pass | fail | not_executable | substitute
```

- **pass**: 期待結果と開発者確認の全項目を、本物の画面・DB・メールで確かめた。
- **fail**: 期待結果を満たさない。製品の不具合か、テストの前提の誤りかは、この時点では決めない。
- **not_executable**: 本物の環境だけでは前提の外部条件を作れない。PSP の成否不明（429 やタイムアウト）を意図的に起こせない、ローカルには公開 URL がないので Webhook の初回自動配送が届かない、など。**何が足りないかを reason に書く。**「他のケースで間接的に裏付けられる」程度では substitute にしない。
- **substitute**: 期待結果の事実は確かめたが、手順の一部を別の方法で確認した。例:
  - 429 は起こせないので、カード拒否が failed に分類され「確認中」の文言が出ないことだけを実機で見て、429 の分類は単体テストが担保する範囲だと明記する
  - ミリ秒単位の失効境界はジョブの日付粒度では狙えないので、消費の順序だけを実ジョブで再現する
  - 処理途中の中断点3つのうち実行できたのは1つだけ、と書き分ける

substitute がある理由: **「迂回して通したものを pass と記録する」ことを禁じるため。** 境界監査の発端は、スモークテストで Checkout のコールバックを迂回して API を直接叩き、それを PASS と記録したことだった。実績では91件中およそ3分の1が substitute になった。substitute を許さないと迂回 pass で埋まる。reason を必須にし、どの層（単体・結合・実機）が担保するかを書く。

結果は `{id, status, at, reason, notes, data}` の形で残し、スクリーンショット・DB のダンプ・メール本文と一緒に証跡ディレクトリへ保存する。

## 3. テーマ別の網羅（15テーマ・代表ケース）

件数は目安。自分のサービスに無いテーマ（委任・旧契約）は落としてよい。

| テーマ | 目安 | 代表ケースと期待結果 |
|---|---|---|
| **初回契約（申込・見積）** | 6 | 無料→有料の申込で、確認画面の本日支払額と次回支払日が決済後の表示・履歴と一致し、履歴は1件だけ増える／上限到達の画面から申込へ進み、ダイアログを閉じただけでは作成できず、支払い後は元のフォームに戻れる／見積の改ざん・期限切れは 409 で拒否し課金しない／同じ見積を2本同時に確定しても契約・支払い・PSP 呼び出しは各1回／初回失敗後に保存カードで再試行すると成功分の1回だけ記録される |
| **金額・日付** | 6 | 基本料＋追加枠N本の税込額／日割りの端数は「税抜を切り捨て→税を切り捨て」の順／最低課金額未満は 0 円で PSP を呼ばず免除理由つきの明細を残す／31日契約は2月だけ月末に丸め3月は31日に戻る／JST で保存し UTC の前日にならない。期末 23:59:59.999 の前後で扱いが切り替わる／負数・小数・Infinity・NaN は例外にし請求額として返さない |
| **上限判定・追加枠** | 6 | 枠購入は、成功なら +1、拒否なら「支払い失敗」、タイムアウトなら「確認中」と見分けられ、成功以外では増えない／同じ操作 ID の再送は二重計上しない／未完了・未払い・解約予約中・上限・権限なし の5状態では買えず、次にやることが案内される／無料で5本同時に作っても1本しか作れない／外部 API を待つ間 DB トランザクションを持ち続けない |
| **更新・カード失敗・再試行** | 6 | 同じ日の月次ジョブを2回走らせても課金は1回／再試行は失敗時に凍結した金額と請求先で行い、最新の見込み額で作り直さない／自動再試行は失敗の3日・7日・14日後だけ。手動操作で日程は狂わない／429 や通信断は unknown として照合に回し督促しない／照合は確実に一致したものだけ成功にする／PSP 成功後に DB 保存が失敗しても charge ID を失わない |
| **カード変更** | 6 | 「カードだけ変更」では未払いを請求しない／複数の未払いをまとめて払ったときは成功・拒否・確認中を行ごとに表示／確認画面を開いた後に状態が変わったら古い確認では確定できない／カード保存の応答が不明なら再入力させず「確認中」と案内する／手動支払いと自動再試行が同時に走っても回収は1件／カードの切替は次回更新から効く |
| **解約・再契約** | 6 | 解約予約をすると期末まで使え、終了前なら取り消せる／無料に残すリソースの選択: 0本なら不要、1本なら自動、2本以上なら選ぶまで確定できない／未払いのまま解約できる。請求しないこととクーポンが失効することを事前に説明する／終了後に遅れて届いた決済成功は記録だけ残し契約は復活させない／通知の送信に失敗しても契約は延びない |
| **クーポン・次回見込み** | 6 | 次回支払日より前に失効する残高は見込みに使わない／見込みの計算に失敗しても 0 円や通常額で埋めない／必要額だけ消費して残りは繰り越す。決済失敗では減らさない／期限の早いものから消費／無効・使用済み・請求書払いへの適用は理由付きで拒否／失効や増額の通知は1回だけ送り、額が変わったら訂正する |
| **第三者支払い（委任）** | 7 | 依頼メールは送信前にプレビューできる／依頼は1件だけ有効。再発行したら古いリンクは無効になり、どの拒否も同じ応答にして内部状態を漏らさない／受諾時: 未契約ならその時点で初回課金、契約中なら次回から切替／支払者が辞退しても当期の請求先は変えない／支払者向け画面で登録前に「いつから」「毎月続く」が分かる |
| **旧来契約（個別契約・請求書払い）の除外** | 10 | 新しい課金の操作 UI を出さない／API を直接呼ばれても拒否／月次ジョブ・停止・督促・増額通知の対象から外す／遅れて届いた成功や失敗は事実だけ記録し契約は変えない／既存の権限を維持 |
| **権限・領収書・計測** | 6 | オーナー以外には操作もカード情報も API の応答も見せない／組織の解決は「一番古い組織」ではなく指定したワークスペースの組織から／領収書の宛名は発行時点で固定／購入イベントは成功時に1回だけ送る |
| **Webhook・返金** | 6 | パス secret とヘッダートークンで認証（不一致は 401 か 404、壊れた JSON は 400、DB 障害は 500）／受信本文を信用せず API で再取得して金額・状態・metadata・livemode を照合／同じイベントが同時に届いても処理は1回／証拠不足・返金済み・終了済みは自動救済しない／返金や紛争は二重に反映せず、通知の失敗は outbox に残す |
| **実接続・運用（メール含む）** | 10 | 本物の Checkout と 3DS を通し、PSP の管理画面と DB が一致／3DS 失敗や拒否の後に正常なカードで1件だけ成功／応答が届かないまま再読み込みしても二重課金しない／処理途中で止まっても1件に収束／各種通知（カード期限、未払い、委任期限、失効、停止）が届き、再送しても課金は繰り返さない／支払いは成功したが公開再開だけ失敗した場合を別の状態として表示 |
| **料金説明・ヘルプ** | 5 | ガイドの計算例が実際の見積と一致／ガイド間のリンクが 404 にならない／Markdown 内の script を実行しない |
| **運営画面** | 4 | 許可リスト以外には 404／申込時の金額とプラン定義の金額を別に表示し、不明な値を推定で埋めない／一覧が上限件数で打ち切られていることを表示／デモ画面は架空データであることを明示 |
| **停止・削除の保護** | 1 | 組織が無料でも、有料契約を持つ単位は無料プランの停止・削除の対象外。処理の直前にもう一度判定する |

## 4. 本物の環境で再現するハーネス

「モックで通した」を pass にしないために、本物のサーバー（`next start` 等の本番ビルド）・本物の DB・PSP のテストモード（sk_test）・ローカルのメール受信箱（Mailcatcher 等）に対して Playwright を回す。

### 構成
```
tests/e2e-real/
  README.md            起動手順・環境変数・レーン・画面文言の実測メモ
  cases/BIL-xxx.spec.ts  1ケース1ファイル
  ledger/cases.json    台帳（人の結果つき）
  support/
    db.ts              TRUNCATE、SQL、型パーサ固定（timestamp を UTC として読む）
    actors.ts          ユーザー作成・ログイン
    scenario.ts        前提を作る（card-profile / subscribe / delegation-send / ...）
    scenario-cli.ts    同じものをコマンドから
    payjp-token.ts     テストカードでトークン作成
    payjp-checkout.ts  本物の Checkout iframe を操作（3DS の選択つき）
    jobs.ts            runJob('cycle' | 'recovery', 論理日付)
    mailcatcher.ts     waitForMail
    record.ts          shot / saveText / record(status, reason)
  evidence/            実行ごとの証跡
playwright.real.config.ts  sk_test / pk_test と DB 名を確認してから起動
```

### 守ること
- **ケースごとに DB を TRUNCATE** してから前提を作り直す。前のケースの残骸で通る／落ちるを無くす。
- **レーンを分ける。** 並列で回すならポート・DB 名・メール受信箱のポートをレーンごとに変える（環境変数 `E2E_REAL_PORT / E2E_REAL_DB / E2E_REAL_MAIL_HTTP / E2E_REAL_SMTP_PORT` など）。共有 DB の結合テストは全件並走で干渉する（規約マスタの一時無効化、レート制限バケット）。
- **`NEXT_PUBLIC_*` はビルド時に焼き込まれる。** サーバーが作る絶対 URL（管理ページのリンク、Webhook の再送先）はレーンのポートに追従しない。spec 側で origin を外すか、BASE_URL を渡す。
- **拒否用テストカードは登録できないものがある。** 登録時に弾かれるカード番号は「登録済みカードでの課金失敗」には使えない。課金時に落ちるカード番号を別に用意する。
- **レーンのサーバーが応答しなくなると Playwright は無出力で固まる。** ポートを kill して再起動する。
- **起動前チェック。** 本番鍵や本番 DB 名なら起動を拒否する。
- 実行は `E2E_REAL_RUN_ID=<run> npx playwright test -c playwright.real.config.ts tests/e2e-real/cases/BIL-xxx.spec.ts` のように run ID を付け、証跡を run ごとに分ける。91件・4レーンで30分程度。

### 実接続テストで見る項目（初回は人がやる）
- 本物の Checkout の iframe を通す。PSP の保護がカード番号の直接送信を拒否するので、トークン注入や強制クリックでは通らない
- DB と PSP の管理画面を突き合わせる: 金額・`paid`・`captured`・`livemode`・3DS の状態・顧客
- 失敗カード: 3DS 失敗 → 正常カードで再試行 → 支払いは1件／拒否カード → 課金 0 件・契約なし／正常カードに切り替えて再試行
- 二重防止: 連打と再読み込み／同じ POST を2本並列で送って 200 と 409 が1本ずつ・課金1件／リクエスト中に再読み込みしてもサーバーが完了し、画面は契約1件・履歴1行
- Webhook をトンネル経由で受ける（ngrok → Webhook のパスだけ通すプロキシ → localhost）。ダッシュボードから本物のイベントを再送する。Webhook のトークンが管理画面の値と一致していること

### 未検証として残す（誠実に書く）
3DS のチャレンジフロー、PSP の初回自動配送、同じイベントの2回再送、公開経路（本番の ingress）、支払い復帰後の本物の再開処理。どれも「本番で最初に起きる」ので、公開日の手順に人の確認として入れる（07）。

## 5. テストを他のモデルに書かせるときの選び方（参考）

同じ指示で複数のモデルに E2E を書かせて比べた経験則。
- 境界の再現（外部 SDK の契約を模す fake など）を含むもの → 高性能モデル単独
- 既存パターンの横展開 → 軽いモデル。「バックグラウンドで待たず同期で回して完走」を指示に入れる
- サンドボックスが localhost に bind できない環境では、生成だけ任せて実行は自分で回す
- 並列比較は git worktree ＋ ポート分離。Playwright の webServer はビルドが長いと空振りするので、サーバーを先に手動起動して reuseExistingServer で拾わせる
