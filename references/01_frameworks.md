# 01 課金設計の8つのフレームと、設計の順番

この資料で決まること
- 仕様を書き始める前に、どの順番で何を決めるか
- 仕様のギャップを「1件ずつ議論する」のではなく「フレームごとに方針を決めて、まとめて消す」やり方
- 仕様が固まったあと、取りこぼしを見つけるストーリーストレステストのやり方

背景: サブスク課金の仕様を12版まで改訂し、独立レビューを2巡、ストーリー検証を99本回した経験から、実際に踏んだ問題を既知のフレームワークに当てはめて整理したもの。次に課金を設計するときは、ストーリーを流す前にこの8つで問題を先回りして潰す。

---

## F1. 「使えるか」と「請求するか」を分ける（Entitlement と Billing）

問い: この機能・リソースについて、「使ってよいかの判定」と「課金額の計算」を別の層で答えられるか。

考え方: 権利（entitlement）のテーブルと、請求（billing）の計算を分ける。プラン変更・既存ユーザーの保護・トライアルは、まず「何が使えるか」で定義し、課金はそこから導く写像として別に決める。Kill Bill や Stripe のドメインモデルの背骨にあたる考え方。

実際に起きたこと: 既存ユーザー保護（グランドファザリング）で「使える」と「請求対象か」を1つの概念で扱っていたため、有償化した後の扱いが決まっていなかった。「無料と言った分」が有償化後に課金対象になるのか、誰も答えられなかった。

---

## F2. 4つの時計を分ける（Service / Billing / Payment / Recognition）

問い: このイベント（解約、スナップショット、決済失敗、返金）は、どの時計で判定するのか。

考え方: 4つの時間軸を最初に分ける。
1. サービスの時計: いつの利用分か（サービス期間）
2. 請求の時計: 請求した時点
3. 入金の時計: 入金した時点
4. 認識の時計: 収益として認識する時点

そのうえで「どの操作がどの時計で効くか」の表を1枚作る。時計の取り違えは、境界まわりのバグの最大の発生源になる。

実際に起きたこと: 「解約期限 23:59:59.999」（サービスの時計）と「課金ジョブの実行時刻」（請求の時計）のどちらが優先するか決まっていなかった。解約フラグに「時刻」の意味がなく、ジョブと操作のどちらが勝つかの順序規則が要った。

---

## F3. 4者を分ける（Payer / User / Owner / Bill-to）

問い: 払う人、使う人、契約の主体、請求書の宛先が全員別人でも、この設計は成り立つか。それぞれが交代したらどうなるか。

考え方: 4者を最初から別のエンティティにする（AWS の Linked Account や Stripe の Customer 分離が例）。「全員同じ人」は特殊ケースであって前提ではない。退職・移管・委任による交代は、通常の流れとして設計する。

実際に起きたこと: 「クライアントのカードで払ってもらう」要件が出てから請求先モデルを作り直した。唯一のオーナーが退職すると誰も解約できない。移譲した後も、退任者の個人カードに課金が続く。

---

## F4. 不変条件ファースト（守るべき式を先に書き、DB制約で機械的に守る）

問い: この設計が絶対に破ってはいけない式は何か。それはコードの注意深さではなく、一意制約やデータ構造で保証されているか。

考え方: 次のような式を最初に書き出す。
- 1サイクルの課金は最大1回
- 二重請求も請求の空白も作らない
- 表示した金額 ＝ 請求する金額
- 期限までに解約すれば請求されない

設計は「不変条件 → 制約 → コード」の順に進める。コードは後から誰かが書き換えるが、一意制約は書き換えに気づける。

実際に起きたこと: 課金試行テーブルを後から足したため、一意キーの定義が章ごとに食い違った。一方の定義どおりに実装すると、二重タブで二重課金が起きる状態だった。

---

## F5. 課金は分散システム（冪等・照会・突合の三点セット）

問い: 外部呼び出しが「成否不明」で終わったとき、次に何をするか決まっているか。帳簿と決済サービスの実績を定期的に突き合わせる仕組みはあるか。

考え方: 外部の決済サービス（PSP）を挟んだ時点で、課金は分散システムになる。対策は3つ。
1. 呼び出しを冪等にする（PSP が冪等キーに対応しているかは最初に確認する。Stripe はある。Pay.jp は無い）
2. 成否不明のときはリトライせず、照会する
3. 突合（reconciliation）ジョブを、保険ではなく設計の中心に置く

Webhook は通知であって、真実ではない。真実は API で取り直す。

---

## F6. PSP に預ける範囲のスペクトラム（機能を借りると制約も借りる）

問い: PSP に何を預け、何を自分で持つか。借りる機能に付いてくる制約（変更できないフィールド、サイクルの規則、上限）を列挙したか。

考え方: Hosted（全部預ける）→ PSP のサブスク機能を使う → 自前エンジン、というスペクトラムの中で立ち位置を決める。経験則は「PSP に預けるのはカード情報とお金の移動だけ。契約の真実（サイクル・状態・金額）は自分で持つ」。

実際に起きたこと: スペクトラムの端から端まで歩いた。PSP の定期課金機能には、顧客を変更できない、課金日がずれる、プラン数に上限がある、といった制約が付いてきて、クーポンや明細の要件と合わなかった。

---

## F7. ライフサイクルは後半から書く（入る／変わる／失敗する／出る／戻る／返す／争う）

問い: 返金、チャージバック、長期滞納からの復帰、解約後の再契約、アカウント削除を、新規契約と同じ細かさで仕様にできているか。

考え方: Subscribe / Change / Fail / Cancel / Return / Refund / Dispute の7つを先に並べ、後半（出る・戻る・返す・争う）から書く。前半は誰でも書けるが、事故は後半で起きる。

実際に起きたこと: レビュー2巡とも、指摘の過半が後半に集中した。返金しても契約が active のまま翌月また課金される、など。

---

## F8. 失敗コストの非対称性（迷ったらユーザー有利に倒す）

問い: この判断で「取りすぎる」失敗と「取り漏れる」失敗の、どちらのコストが大きいか。

考え方: 取りすぎ（二重課金、約束に反する課金）は信頼を損ない、返金対応の固定費も生む。取り漏れは軽い機会損失で済む。したがって既定は次のとおり。
- お金はフェイルクローズ（課金しない側に倒す）
- サービスはフェイルオープン（止めない側に倒す）

この原則を最初に明文化しておくと、その後の個別判断が速くなる。

---

## 設計の順番（7ステップ）

1. **不変条件を書く（F4）** 破ってはいけない式を4〜6個書き、それぞれを守る一意制約・データ構造と対応づける。
2. **4つの時計と4者の表を作る（F2・F3）** 「操作 × 時計」のマトリクスと、Payer/User/Owner/Bill-to の交代シナリオを1枚ずつ。
3. **権利と請求を別の層に分ける（F1）** プラン・保護・トライアルをまず「何が使えるか」で定義し、課金はその写像として決める。
4. **PSP に預ける範囲を決める（F6・F5）** 冪等キー対応の有無を最初に確認する。契約の真実は自分で持つ。突合ジョブを設計に入れる。
5. **ライフサイクルの後半から仕様を書く（F7）** 返金・紛争・滞納からの復帰・解約後・削除。ここが新規契約と同じ厚みになるまで、前半は書かない。
6. **迷った判断は非対称性で倒す（F8）** お金はフェイルクローズ、サービスはフェイルオープン。
7. **検算としてストーリーの直積テストを回す** 状態 × 時刻の境界 × 同時操作 の組み合わせで流す（下記）。フレームで先回りした後の取りこぼし検出に使う。

使い方のコツ: ギャップを1件ずつ議論しない。フレームの順（F4 → F1 → F2 → F3 → F7 → F6/F5）に方針を1つずつ決めると、1つの決定で配下の複数のギャップがまとめて消える。個別のストーリーは、決めた方針の検算に使う。

---

## ストーリーストレステストのやり方

仕様が一通り書けたら、具体的な人物・日付・操作でストーリーを流し、仕様がどう答えるかを見る。

### 生成
- 10のレーンに分けて、1レーン10本ずつ、計100本前後を作る。
  1. 有償化・初回課金
  2. サイクル・従量
  3. 支払い失敗・督促
  4. 解約・終了・再契約
  5. クーポン
  6. 第三者による支払い（委任）
  7. 組織・権限
  8. 移行・グランドファザリング
  9. 返金・経理
  10. タイミング競合（期末、同時操作、ジョブとの衝突）
- 各ストーリーは「具体的な人物・日付・操作」で書く。「ある日ユーザーが」ではなく「3月31日に申し込んだAさんが4月30日23:58に解約ボタンを押した」。
- 判定は2値。「OK（仕様に答えがある）」か「困る・要判断（答えがない、または矛盾する）」。

### 検証
- 「困る・要判断」は全件、生成した人とは別のエージェント（または人）が、仕様の原文と PSP の公式ドキュメントに突き合わせる。仕様に答えがあったものは誤検出として除外する。
- 残ったギャップを性質ごとに8つ前後のテーマに束ね、F1〜F8 に対応づける。テーマ単位で方針を決めると、配下のギャップがまとめて消える。

### 実績の目安
99本流して、確定したギャップ85件（金銭リスク36、停止リスク2、体験17、運用22）、誤検出3件。ギャップの8テーマは次のとおりだった。
1. 仕様内の改訂の残骸で、二重課金防止が効かない（一意キーの定義が章ごとに矛盾。成否不明を受け止める状態がない）→ F4 / F5
2. 既存ユーザー保護と有償化の境界が決まっていない → F1
3. 期末・解約と課金ジョブの競合 → F2
4. 従量の数え方が未定（停止中のリソースを数えるか、数える基準時点、アンカー日を保持するフィールド）→ F2
5. 未収と委任・復帰の交差（誰の借金か。長期停止からの復帰時に停止中の分を請求するか）→ F3
6. 組織権限の単一障害点（オーナーが消えると誰も解約できない）→ F3
7. 返金・チャージバックの後処理（返金しても契約が動き続ける）→ F7
8. 保存カードでの初回課金と 3DS の適法性（PSP・カード規則の外部確認が必要）→ F6

エージェントで回すなら、生成10レーン＋検証3の構成で1回で済む。人で回すなら、レーンを2〜3に絞って「失敗する・出る・戻る」を優先する。
